What changed from the original plan, and why

The original plan (v1) was funded on four co-equal pillars: (A) feature search over framework source, (B) mock-LLM testing, (C) knowledge management, (D) local evals. Under scrutiny, A and B turned out to be things a competent coding agent (e.g. Claude Code) already does as a side effect of building the agent it's asked to build — a developer who says "build me a LangGraph agent that does X, with mocked-LLM unit tests for the routing logic" gets both A and B for free, with no separate Studio to install.

This draft keeps only C and the compliance-critical slice of D, promotes what was a minor "addendum" feature (the Requirements → Rubric → Claude Code Review pipeline) into the product's spine, and replaces the original's specific $390K/$238K Year‑1 targets with a validation‑first Phase 0 — see What Changed and Financial Model.

1. Executive Summary

Agentic AI frameworks — LangChain, LangGraph, DeepAgents, CrewAI, AutoGen — have become enormously capable and enormously large. A developer building with them today typically has a general-purpose coding agent (Claude Code or equivalent) already doing the heavy lifting: it already knows the frameworks' idioms, already writes mocked-LLM unit tests when asked, and already assembles the deterministic control flow from a plain-language spec. Any product pitched as "helps you find the right feature" or "helps you test without spending on LLM calls" is competing with a capability the target buyer already owns.

What a coding agent does not do on its own: hold a persistent, versioned, inspectable record of what a given agent knows as it evolves release over release, and enforce a repeatable, standardized, audit-ready structure around code reviews and evals — the kind of artifact a second engineer, a manager, or a compliance reviewer needs before trusting an agent that's about to leave one person's laptop.

Agent Dev Studio (v2) is built on exactly those two surviving capabilities: a Knowledge Ledger that tracks what an agent knows and how that changes over time, and a Compliance-Grade Review & Eval Harness that turns a structured requirements form into a Claude-Code-driven review or eval run, with fixtures, findings, and reports kept local and standardized across projects.

Revenue mechanism unchanged in shape — a Free tier feeding a Pro tier at $195/year — but the specific Year‑1 targets from v1 (2,000 subscribers / $390,000 revenue) are not carried forward. They were derived from a funnel sized for a broad, four-pillar, solo-developer audience that no longer matches this narrower, team-oriented product. See Financial Model for what replaces them.

Before any Studio code beyond a CLI prototype is written, this plan calls for a Phase 0 validation step (3–4 weeks): interviews with 8–12 teams past the solo-prototype stage, plus 20–30 real runs of the standalone Review Harness, specifically testing whether the surviving pillars are themselves substitutable by "just ask the coding agent directly." See Go-to-Market.

2. What Changed — Why Two of Four Pillars Were Cut

Original pillar (v1)Verdict under "just ask the coding agent" test
A. Feature Search (vector DB)
Cut		The problem statement was "no fast way to find the relevant features among 2,400 files." That's exactly the retrieval-and-synthesis task a coding agent already performs when given a plain-language build request — and it does so understanding framework idioms, not just text similarity over raw source. A bespoke vector index is arguably a worse tool for this than the coding agent the buyer already uses.
B. Mock LLM Testing
Cut as headline product		Real problem (test deterministic logic without burning LLM spend), ordinary solution: "write pytest with mocked LLM calls" is a standard coding-agent request. Not a reason to buy a separate scenario-library app. May survive as a minor utility inside the Review Harness, not as a funded pillar.
C. Knowledge Management
Kept — primary pillar		Survives. This is a runtime-introspection question (what does this deployed agent currently know, and how has that changed) — not a code-generation question. A coding agent doesn't do this as a side effect of anything.
D. Local Evals
Kept — narrowed		Partially survives. The fixture/test-data privacy angle is real. The broader "avoid cloud dependency" framing does not fully hold: if the org already routes its source code through a cloud coding agent to build the thing, the general cloud-avoidance pitch is inconsistent. The honest, narrower claim is "keep review fixtures and findings off third-party eval services" — kept on that basis.
The plan indicted itself, twice
  • v1's own time estimate assumed Claude Code was capable enough to build the Studio's four bespoke subsystems (vector pipeline, mock-LLM engine, eval harness, knowledge tracker) for the founder. If a coding agent is judged that capable, it is trivially capable of building one much narrower thing — a single customer's agent — directly for the end user, with no packaged product as an intermediary.
  • v1's "Code Reviewer" addendum (now promoted — see Deep Dive) described its own mechanism as: collect requirements, convert to JSON, hand to a Claude Code prompt, let it do the work. That pattern is a tacit admission that "describe requirements, let the coding agent build it" is a viable product shape — the same shape that undercuts pillars A and B. This draft leans into that insight instead of ignoring it: the pattern becomes the core architecture, not a footnote.

3. The Product — Two Surviving Pillars

What it is

A downloadable Studio application (with a companion CLI for CI use), narrowed from four capabilities to two — plus a thin utility layer that survives only as a minor Pro convenience:

1. Knowledge Ledger primary pillar
An inspectable, versioned record of what a given agent knows — tools, retrieved documents, memory, context — with a diff view release over release. "Quiz mode" lets a user ask the ledger what the agent currently knows and compare it against what it knew last release. Explicitly not a code-generation tool: it observes and records, it doesn't build.
2. Compliance-Grade Review & Eval Harness primary pillar
A Requirements Template converted to JSON drives a Claude-Code-executed review or eval run against the local repo, scored against a universal + framework-specific rubric. Fixtures, findings, and the raw report stay local. Full detail in the Deep Dive.
Feature Search (vector DB) cut
Revisit only if Phase 0 user research turns up a concrete case where a coding agent's own framework knowledge demonstrably underperforms a bespoke index — not assumed up front.
Mock LLM Testing (standalone) demoted
A thin "save/replay a mock scenario" utility may still live inside the Review Harness, but it is not sold on its own and is not part of the funded product.
User journey (revised)
  1. Developer or team builds their agent however they already do — most commonly, with a coding agent like Claude Code.
  2. When the agent is ready to leave one person's laptop — a second engineer, a manager, or a compliance reviewer needs to trust it — they install Agent Dev Studio (free tier).
  3. They run the Compliance-Grade Review & Eval Harness against the repo: a Requirements Template drives a structured, rubric-based review and eval, producing a standardized report.
  4. They use the Knowledge Ledger to record what the agent currently knows, and to diff that against the last release as the agent evolves.
  5. On a Pro subscription, they get multi-agent, historical tracking and the full review/eval depth and rubric library.

4. Target Market

Primary customer persona (narrowed from v1): teams — not solo builders — where an agent is about to leave one person's laptop: a second engineer, a manager, or a security/compliance reviewer needs to trust it without re-deriving what it does from scratch. Building with LangChain, LangGraph, DeepAgents, or CrewAI.

Two segments worth calling out specifically:

Small engineering teams past the prototype stage
The moment "it works on my machine" stops being sufficient. Need a shared, versioned record of what the agent knows and a standardized review report a teammate didn't have to write from scratch.
Regulated / data-sensitive enterprises
Banking, insurance, healthcare, government contractors. The pitch here is narrower and more honest than v1's: "keep review fixtures and findings local," not "avoid the cloud entirely" — see Moat.

Explicitly deprioritized: the individual solo-builder segment v1 leaned on heavily for the now-cut pillars. That segment's default behavior — "just ask my coding agent" — is the substitution risk, not a customer profile to chase. Reached, when relevant, through the same LangChain/LangGraph/DeepAgents/CrewAI developer ecosystem as v1 (Discord, GitHub, forums, conferences) — see Go-to-Market.

7. Go-to-Market — Validation-First

Why Phase 0 exists

v1 went straight from thesis to a 6-month solo build. This draft inserts a validation step before that commitment, because the two surviving pillars are also the two with the least existing evidence of demand — v1 itself flagged Knowledge Management as having "no direct incumbent competitor," which is a demand-risk flag as much as it is a moat claim, until proven otherwise.

Phase 0 — Validate (3–4 wks)
  • Interview 8–12 teams past the solo-prototype stage: "when an agent changes, how do you know what changed, and who signs off?"
  • Ship the Review Harness alone as a free CLI script — no Studio, no UI — get 20–30 real runs against real repos
  • Kill criterion: if teams say "I'd just ask my coding agent to review this myself" as often as they said it about the cut pillars, this pillar is also substitutable and the plan needs a third pivot
Phase 1 — Build (only if Phase 0 validates)
  • Build the two surviving capabilities end to end plus Free/Pro gating and billing, ready but not yet turned on
  • Distribute exclusively through free channels: personal network, Discord/GitHub, private beta testers
  • Materially smaller build surface than v1's four-capability MVP — see Time Estimate
Phase 2 — Launch & Monetize
  • Flip on the Pro tier and billing; public launch via Hacker News/Product Hunt
  • Turn on a marketing budget sized from Phase 0 signal, not assumed in advance
  • Convert the backlog of free users accumulated in Phase 1
Phase 3 — Optimize the Funnel
  • Improve free → paid conversion using real Phase 2 data, not the v1 assumption
  • Reduce early churn on the paid tier
  • Re-run the revenue model (see Financial Model) with real numbers

Core GTM channel (unchanged mechanism from v1): organic, community-driven distribution inside the LangChain/LangGraph/DeepAgents/CrewAI developer ecosystem. Paid marketing is a support lever switched on only once monetization begins and only at a budget size Phase 0/2 evidence supports.

8. Flagship Acquisition Strategy — Agentic AI Interview Challenges

Carried forward from v1 without material change to the mechanic — if anything, this matters more now, because the core value proposition is thinner (two pillars instead of four) and needs a stronger top-of-funnel hook to earn the first look. A free, standalone lead magnet: Agentic AI interview challenges. Tech professionals download Agent Dev Studio specifically to prepare for job interviews by building a real Agentic AI system against a realistic business specification — no payment, no signup wall, entirely free.

How it works
  1. Candidate picks a domain — e.g., Insurance, Banking, or other Financial Services.
  2. The Studio pulls a real, business-specific challenge for that domain from the Industry Challenge Catalogue (see Industry Challenge Catalogue) — a concrete business problem drawn from an actual company's key processes, not a generic toy exercise.
  3. The candidate builds an Agentic AI system that solves the stated problem (using whatever coding agent they prefer), then runs it through Agent Dev Studio's Review & Eval Harness and records it in the Knowledge Ledger — the two surviving capabilities, applied to their own portfolio project.
  4. The finished build, plus a standardized review report, becomes a portfolio artifact the candidate can walk through in an actual interview — every step ran on the free tier.
Why this is the flagship channel, not just another one
  • Self-selecting, high-intent audience. Someone downloading a tool to prepare for an Agentic AI interview is, by definition, exactly the developer this product is built for.
  • Built-in virality. Interview prep is discussed openly on LinkedIn, Reddit, and Discord — a strong "I used this to land the interview" story is one of the most shareable growth loops available to a dev tool.
  • Domain depth doubles as credibility. Business-specific, realistic challenges (see Industry Challenge Catalogue) make the free tool look and feel like an enterprise-grade product from the very first download, reinforcing the enterprise wedge described in Strategic Advantage / Moat.
  • Zero incremental cost to the funnel. This rides entirely on the existing free tier and the content/community channels — it sharpens the hook on existing distribution effort rather than adding new spend.
  • Now leads with what actually differentiates the product. Because the candidate's build is fed through the Review Harness and Ledger rather than a feature-search or mock-testing demo, the acquisition motion itself demonstrates the two pillars that survived scrutiny.

9. Mobile Agentic AI Builder Challenge

Carried forward from v1 without material change. The fastest way to start learning what developers actually need is to give them something they can pick up in a spare five minutes, on the device already in their hand. The Mobile Agentic AI Builder Challenge is a tiny, phone-friendly web app, built in plain JavaScript, that simulates the core pattern of LangChain's Python agent framework entirely in the browser — no install, no desktop, no signup. Still planned as an early, lightweight product, ahead of the full Agent Dev Studio, specifically to get real users engaging and to start collecting feedback.

How it works
  1. User opens the app on their phone — a lightweight, mobile-responsive JavaScript page with no download required.
  2. The app poses a small, concrete business problem and hands the user a fixed toolkit of pre-built JS "tools" (functions such as a mock retriever, a router, a calculator, a data lookup) — a deliberately simplified stand-in for LangChain's Python tool/chain primitives.
  3. The user wires the given tools together on-screen to assemble a small Agentic AI solution to the stated problem — the same "pick the right tool, chain it correctly" thinking a real agent build requires, compressed into a few taps.
  4. The user runs their build against a bundled set of test cases; the app immediately reports how many test cases passed vs. failed — a small, self-contained preview of the pass/fail reporting the full Review & Eval Harness does for real projects.
How it feeds the rest of the plan (updated)

This mobile challenge is not a separate business line — it is the earliest, lightest rung on the same ladder described in Go-to-Market and Agentic AI Interview Challenges. A user who enjoys solving the mobile challenge is a warm lead for the full free-tier Agent Dev Studio download, and its pass/fail reporting is now framed as a preview of the Review Harness rather than of a mock-LLM-testing product that no longer exists as a funded pillar. Feedback from Phase 0 and this challenge together should inform which parts of the Ledger and Harness (see The Product) to prioritize first.

10. Industry Challenge Catalogue — 100+ Financial Services Businesses

Unchanged from v1 — this content is independent of the pillar cuts. To make the challenges in Agentic AI Interview Challenges realistic rather than generic, the plan works through the businesses of 100+ leading Financial Services companies — spanning Banking, Insurance, and adjacent Financial Services — to identify the handful of key business processes that most directly impact each company's bottom line. Those processes are consolidated into a single challenge catalogue; when a candidate picks a domain, a matching business-process challenge is pulled from the catalogue and turned into their build spec.

Catalogue-building pipeline
  1. Work through each company below and identify its 3–5 highest-impact business processes (e.g., claims adjudication, underwriting, loan origination, fraud detection, trade settlement).
  2. Write each as a standalone business problem statement, independent of any one company's internals, so it reads as a generic industry challenge rather than a case study of a named company.
  3. Tag each problem by domain (Banking / Insurance / Other Financial Services) and sub-industry, and add it to the catalogue.
  4. When a candidate selects a domain in the Studio, a challenge is pulled from the matching catalogue entries and presented as their build spec.

13. Strategic Advantage / Moat

  • Local-first is still an enterprise wedge — narrowed and more honest. The Review & Eval Harness keeps fixtures, findings, and reports off third-party services, sidestepping the security-approval cycle for that specific workflow. This draft does not claim it avoids cloud dependency generally — the org's coding agent already routes source code through a cloud provider during the build itself, and overselling the broader claim risks credibility the first time a buyer notices the inconsistency.
  • Price removes the procurement blocker — $195/year is low enough for an individual engineer or small team to expense or self-pay, with no approval process required.
  • Knowledge Ledger is a new category — tracking what an agent concretely knows and how that changes over time has no direct incumbent competitor at time of writing. Treated here as a moat candidate, not a proven one — see the matching entry in Risks.
  • The Ledger-Harness pattern compounds with rubric depth — as framework-specific rubrics (LangGraph, CrewAI, and later AutoGen/DeepAgents) mature, the Review Harness becomes more valuable and harder for a late entrant to replicate quickly, replacing v1's "feature-search index" moat claim with one that survived scrutiny.
  • Unit economics — deferred, not asserted. v1 claimed a specific ~$10 cost-per-paying-subscriber; that number was derived from the now-retracted funnel and is not restated here. Revisit once Phase 0/2 produce real acquisition-cost data.

16. Deep Dive — Compliance-Grade Review & Eval Harness core product

In v1 this was a late "feature addendum" (the Agentic AI Code Reviewer) bolted onto a four-pillar Studio. In this draft it is promoted to one of the two pillars the entire business is funded on (see The Product) — the pattern it uses (Requirements Template → structured rubric → Claude-Code-driven review → standardized report) turned out to be the one part of v1 that didn't compete with a coding agent, because it wraps a coding agent's output in structure and an audit trail rather than trying to out-build it.

The gap this closes — vs. asking a coding agent directly, and vs. LangSmith
CapabilityAsk a coding agent directly, ad hocCore LangSmithLangSmith Engine (2026)This Harness
What it looks atWhatever the user thinks to ask about, in whatever format the agent returnsRuntime traces & datasetsRuntime traces, and connected repo code — but only once a failure is observedThe actual source code, on demand, against a fixed rubric, independent of any observed failure

The honest differentiator is not "does something a coding agent can't do" — a coding agent can review code if asked. It's repeatability, structure, and an audit trail that ad hoc requests don't produce on their own, and that neither LangSmith variant provides proactively, independent of a failure signal.

How it works — end to end
1

Requirements Template (form) — project, framework (LangChain/LangGraph or CrewAI), agents & intended scope, non-negotiable business rules, fault lines to check — converted to a single JSON object.

2

Review Prompt harness — combines the JSON with the Ten Agent Fault Lines (universal) and a framework-specific rubric (LangGraph or CrewAI idioms), and builds a Claude Code review prompt pointed at the project's actual source.

3

Structured findings — Claude Code reviews the code (not run, not modified) and returns severity-tagged findings per agent, per fault line, and per business rule.

Standardized HTML Report

The same underlying mechanism also drives the eval side of this pillar: a Requirements Template plus a fixture set produces a local, standardized eval run and report, with the fixtures and findings never leaving the network.

The review rubric — universal + framework-specific layers

Split into two layers so new frameworks can be added without rebuilding anything.

Layer 1 — Universal: the Ten Agent Fault Lines

Each fault line is assessed structurally in the code as Present / Partial / Missing, with file/line evidence. This is the layer that still runs even for a framework without a Layer 2 rubric yet — see the roadmap below.

Layer 2 — LangChain / LangGraph (Phase 1)

  • Typed graph state, not a loose dict
  • One responsibility per node — no "god node"
  • Explicit, testable conditional routing
  • Deliberate checkpointing/persistence
  • Typed tool schemas, not raw string parsing
  • Proper interrupt/resume for human-in-the-loop
  • Recursion/step limits set
  • State scoped per thread/session ID

Layer 2 — CrewAI (Phase 1)

  • Each Agent's role/goal/backstory scoped to one responsibility
  • Every Task has an explicit expected_output
  • Tools assigned only within an agent's intended scope
  • Process type (sequential/hierarchical) matches the need
  • Manager delegation boundaries explicit, if hierarchical
  • max_iterations/timeout set at the crew level
  • Memory usage deliberate, not left on by default
The standardized HTML report

Every report — regardless of project or framework — carries the same sections: a header (project, framework, depth, timestamp, AI-generated-review disclaimer), an executive summary scorecard (Architecture Soundness, Fault-Line Coverage, Framework Idiom Adherence, Business-Rule Compliance), a Ten Fault Lines table, a framework rubric table, a business-rules table, one collapsible card per agent with severity-tagged findings, and an appendix with the exact prompt and raw findings JSON used — so a user comparing reports across several projects can do it at a glance. This standardized, comparable structure is the part an ad hoc "review this for me" request to a coding agent does not reliably produce twice in a row.

17. Summary

Agent Dev Studio (v2) narrows v1's four-pillar pitch to the two capabilities that survive the test "why wouldn't a developer just ask their coding agent to do this directly": a Knowledge Ledger that tracks what an agent knows over time, and a Compliance-Grade Review & Eval Harness that turns ad hoc "review this for me" requests into a repeatable, standardized, audit-ready report — the pattern v1 buried as a late addendum and this draft promotes to the product's spine.

The revenue mechanism (Free → $195/year Pro) is unchanged in shape, but v1's specific $390,000/$238,000 Year‑1 targets are not carried forward — they were built on a funnel sized for the two cut pillars and a broader audience than this draft now targets. In their place: a Phase 0 validation step (8–12 customer interviews, a standalone CLI harness run against 20–30 real repos, and an explicit kill criterion) before any further build investment, with the revenue model in Financial Model to be rewritten from that evidence rather than reasserted from the original thesis.
