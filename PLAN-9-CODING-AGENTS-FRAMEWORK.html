Executive Summary

Large enterprises are using agentic AI coding tools (Claude Code, Codex, and similar platforms) to accelerate legacy modernization — the leading edge case being multi-million-line COBOL-to-Java migrations. The capability is real: these models understand COBOL semantics and idiomatic Java well. But the quality of the output is wildly inconsistent — from file to file, developer to developer, and project to project, even within the same engagement.

The deeper obstacle is not model capability or process discipline alone — it's trust. A COBOL shop with a 10-million-line estate, dozens of contributors, and decades of undocumented business logic will not hand a vendor broad access, let alone route core logic through a third-party LLM, on a pitch. They need to see proof, on their own code, before they'll extend any further access. A "we'll discipline your coding agent's inputs" pitch is a harder sell than "point this at your own COBOL and get back working Java that's byte-for-byte identical to what your mainframe already produces" — the second one earns the first meeting.

Coding Agents Framework (CAF) has pivoted accordingly (August 2026): the lead product is now a free, 100% deterministic COBOL-to-Java converter — no LLM in the conversion path at all, so no context-window chunking problem and no prompt-quality variance to manage. It parses the COBOL source directly and generates working Java, together with an automatic correctness proof (a byte-for-byte diff against the program's real output). This has already been proven against two independent COBOL Batch codebases with byte-for-byte identical results. The roadmap now extends that same deterministic engine to DB2 database access, IMS databases, CICS/IMS online transaction programs, and VSAM files — the rest of a typical mainframe estate beyond batch. Where a piece of legacy code is too irregular for full determinism, CAF falls back to its original discipline-as-code path: automated chunking, metadata extraction, and versioned prompt packs handed off to whatever coding-agent platform the team already uses. CAF also ships an Eval Framework — a local, zero-cloud-dependency proof harness today, with a LangSmith-backed harness layered on top for teams that want centralized, program-wide eval tracking.

The framework itself is free. The entire revenue plan is still one number: reach at least 100 tracked customers with LangSmith access attributable to this framework, then convert that proof into a flat $250,000/year referral fee from LangChain for driving enterprise adoption of LangSmith as the eval backend for legacy modernization work. The pivot changes how those 100 customers are won — leading with a free, provably-correct deterministic tool instead of a discipline-layer pitch — not the underlying monetization mechanism.

This is still a concentrated, single-counterparty revenue model with real chicken-and-egg risk: LangChain will not sign the deal on a pitch alone, and the 100-customer proof has to be built before the deal exists. It also now carries a real technical-scope risk of its own — determinism is proven for Batch, but not yet for DB2, IMS, CICS/IMS Online, or VSAM. See Path to $250K/Year and Risks & Mitigations.

2. The Problem

#ProblemWhy it hurts
1Context overload from naive chunking. COBOL batch programs are frequently single files of 5,000–20,000+ lines with deeply nested paragraph structures and GOTO-driven control flow.Pasting a whole program, or splitting it at arbitrary line boundaries, either exceeds useful context or severs paragraphs from the working-storage and condition-name definitions they depend on — the model starts hallucinating field types and business logic it can no longer see.
2Invisible, undocumented metadata. Copybooks are shared across dozens of programs; CICS maps, IMS PSB/DBD hierarchies, and DB2 DDL/referential structure exist outside the source files a developer would naturally paste into a prompt.Without this assembled as structured context up front, the coding agent is inferring record layouts and relationships it should be able to look up — the single largest source of subtly wrong conversions that pass a superficial code review.
3No shared process across developers or teams. Absent a common framework, each developer invents their own ad hoc chunking and prompting approach.Quality varies file to file and team to team on the same migration program — a governance problem, not a per-developer skill problem, and one that gets worse as the program scales to more contributors.
4No systematic way to measure conversion quality at scale. Spot-checking a sample of converted programs doesn't scale to 10 million lines.Building golden datasets and eval harnesses from scratch, per project, is expensive and in practice rarely done with any rigor — so quality problems surface in UAT or production instead of during conversion.
5Trust is the actual first-sale bottleneck. A modernization program lead has no reason to extend a new vendor broad access to a 10-million-line estate, or to route core business logic through a third-party LLM, without proof it's worth the risk.A discipline-layer pitch ("we'll structure your coding agent's inputs") asks for trust before delivering proof. A tool that converts a shop's own sample code and hands back a byte-for-byte correctness report earns that trust in a single meeting instead of a sales cycle.

There is currently no widely adopted, free, purpose-built framework that enforces the chunking, metadata, and eval discipline a large legacy modernization program needs — independent of which coding-agent platform the team uses to actually generate the code — and no free tool that proves its own correctness on a shop's own code before asking for any commitment. That combined gap is the business opportunity.

3. The Product & How It Works

What it is

A downloadable Coding Agents Framework (CAF), led by a free, 100% deterministic COBOL-to-Java conversion engine — it parses COBOL source directly and generates working Java itself, with no LLM anywhere in the conversion path, plus an automatic correctness proof (a byte-for-byte diff against the program's own real output) attached to every conversion. Where legacy code is too irregular for full determinism, CAF falls back to its original discipline-as-code tooling: Python tools and a prompt library that structure the inputs to whichever coding agent the team already uses. An Eval Framework sits underneath both paths and measures the output.

A. Deterministic Conversion Engine Lead product
Parses COBOL directly and generates working, idiomatic Java — proven byte-for-byte identical to the source program's real output before a human reviews a line. Live today for COBOL Batch; DB2, IMS databases, CICS/IMS online programs, and VSAM files are next (see MVP scope below).
B. Eval Framework
A local, zero-cloud-dependency byte-diff harness that's already the proof mechanism behind the deterministic engine's own claims, plus a golden-dataset generator and a LangSmith-backed harness layered on top for teams that want centralized, program-wide eval tracking.
C. Discipline-as-Code (fallback path)
The original chunking engine, metadata extraction pipeline (copybooks, CICS maps, IMS PSB/DBD, DB2 DDL, call graphs), versioned prompt library, and orchestration CLI — retained specifically for whatever code shape resists full determinism, handed to the team's own coding agent.

MVP scope — COBOL → Java, modularized by legacy subsystem, sequenced by how much of a typical mainframe estate each one unlocks once the deterministic engine covers it:

PackStatusWhy it's sequenced there
COBOL BatchProvenLarge, sequential programs — the highest-volume, most common entry point for a modernization program. Already converted, byte-for-byte identical to the original, against two independent real codebases.
VSAMNextKeyed/indexed file access underneath much of the batch and online estate — deterministic coverage here is a prerequisite for fully covering both DB2/IMS-adjacent batch jobs and online programs, not just its own standalone pack.
DB2NextEmbedded SQL / relational database access inside COBOL programs — the next most common dependency after batch file I/O, with a well-standardized (if verbose) access pattern to convert deterministically.
IMS (databases)NextHierarchical database navigation (PSB/DBD, GET UNIQUE/GET NEXT) — a fundamentally different access pattern than DB2's relational calls, and less standardized across shops.
CICS / IMS OnlineNextPseudo-conversational transaction programs with BMS maps or IMS message processing — the biggest lift of the four, since it changes the execution model itself (transaction-driven, not a linear batch run), not just the I/O being converted.

DB2/IMS/Online/VSAM are new build, not yet prototyped — treat their scope and timeline as considerably less certain than the proven Batch pack (see Estimate of Total Time for Year 1's revised workstream table).

User journey
  1. Team downloads and installs CAF locally — free, no signup wall.
  2. They point CAF at the COBOL/JCL/copybook/DB2-DDL/IMS-PSB-DBD source tree.
  3. CAF classifies each program by subsystem type. For anything the deterministic engine covers (Batch today; VSAM/DB2/IMS/Online next), CAF converts it directly and generates working Java — no LLM involved, no context-window chunking to get right.
  4. Every deterministic conversion comes back with an automatic correctness report: a byte-for-byte diff against the program's own real output, run against real test data.
  5. For whatever code shape isn't yet covered deterministically, CAF falls back to the original discipline-as-code path — metadata extraction and ready-to-use prompt packages, handed to the developer's own coding agent (Claude Code, Codex, or others).
  6. Either path lands in the same Eval Framework — local proof by default, with a LangSmith-backed harness for teams that want centralized, program-wide tracking across every conversion.

CAF is local-first and proves itself before asking for trust — the deterministic engine and all core tooling run on the developer's own machine, and the fallback discipline-as-code path remains BYO-LLM and works with any coding-agent platform

4. Target Market

Primary customer persona: systems integrators running large COBOL mainframe modernization engagements on behalf of enterprise clients, and enterprise internal modernization/platform teams running the migration in-house.

Best starting industries (large legacy COBOL footprints, well-documented compliance pressure, clear ROI on getting the conversion right):

1. Banking & Financial Services
Core banking, payments processing, batch settlement — some of the largest and oldest COBOL estates in existence.
2. Insurance
Policy administration, claims processing — deep CICS/IMS/DB2 footprints, heavy batch processing.
3. Government & Public Sector
Benefits administration, tax systems — long-running mainframe estates under increasing modernization mandates.

Systems integrators are the highest-leverage channel, not just a segment. An SI adopting CAF as an internal accelerator gets a standardized, repeatable process across every client engagement — a much faster path to the 100-customer target (see Reaching 100 LangSmith-Referred Customers) than enterprise-by-enterprise adoption alone. These industries also happen to have the broadest legacy footprint — batch, online (CICS/IMS), and both relational (DB2) and hierarchical (IMS) databases, often over VSAM — which is exactly where the deterministic-first roadmap is headed and where a working proof lands hardest.

12. Strategic Advantage / Moat

  • A working, provably-correct deterministic converter is a faster and stronger trust-building artifact than any pitch — a prospect can see byte-for-byte proof against their own code before committing to any process change, which shortens the sales cycle in a way a discipline-layer-only product structurally can't.
  • Domain-specific engineering is hard to replicate quickly — building a deterministic conversion engine (not just a metadata extractor) for VSAM, DB2, IMS, and CICS/IMS Online correctly requires real legacy-systems expertise, and each subsystem's execution model is different enough that there's no shortcut across them.
  • Zero price removes the adoption blocker — no budget approval, and because both the deterministic engine and the fallback tooling run locally, much less security-review friction than a paid or cloud-only alternative.
  • SI channel distribution advantage — landing a framework as an internal accelerator inside a systems integrator reaches every one of that SI's client engagements, not just one customer at a time.
  • The golden-dataset/eval infrastructure is the hard-to-replicate part — and it's no longer just a claim: it's already the mechanism proving the deterministic engine's own byte-for-byte correctness. That infrastructure is what a modernization program manager actually needs before cutover, and what anchors the LangChain relationship.
  • Strong unit economics if the deal signs — near-zero marginal cost per additional customer once the tooling exists, against a flat $250,000/year fee that doesn't scale down with a smaller team.

15. Summary

Coding Agents Framework addresses a real, underserved gap in agentic-AI-driven legacy modernization — and, as of the August 2026 pivot, addresses it by leading with proof instead of a pitch. The inconsistency in COBOL-to-Java conversion quality is a process-discipline problem, not a model-capability problem, but the actual first-sale bottleneck in a COBOL shop is trust: no vendor earns broad access to a 10-million-line estate without demonstrating correctness first. CAF's lead product is now a free, 100% deterministic COBOL-to-Java converter — no LLM in the conversion path, an automatic byte-for-byte correctness proof on every conversion — already proven on COBOL Batch across two independent real codebases, with VSAM, DB2, IMS, and CICS/IMS Online next. The original discipline-as-code tooling (chunking, metadata extraction, prompt library) remains as the explicit fallback for whatever resists full determinism.

The product is still free by design, because the business is not selling the framework; it's building a qualified, attributable enterprise pipeline into LangSmith, monetized through the same single flat $250,000/year referral fee. That model is only as strong as the proof behind it: reaching ≥100 real, trackable customers with LangSmith access before or during negotiation with LangChain is still the load-bearing milestone the entire plan depends on. The pivot strengthens the customer-acquisition motion but adds real technical-scope risk of its own — the revised build estimate is roughly double the original (§9), and determinism is proven only for Batch, not yet for VSAM, DB2, IMS, or CICS/IMS Online. The single-counterparty concentration, the chicken-and-egg sequencing, the local-first-vs-cloud-eval tension, and now the open question of how far full determinism actually generalizes are the risks most likely to determine whether this plan works.
