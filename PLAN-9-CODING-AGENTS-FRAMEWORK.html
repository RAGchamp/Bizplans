Executive Summary

Large enterprises are using agentic AI coding tools (Claude Code, Codex, and similar platforms) to accelerate legacy modernization — the leading edge case being multi-million-line COBOL-to-Java migrations. The capability is real: these models understand COBOL semantics and idiomatic Java well. But the quality of the output is wildly inconsistent — from file to file, developer to developer, and project to project, even within the same engagement.

The root cause is not model capability. It's process discipline. Developers feed the coding agent poorly chunked source — a 5,000–20,000 line COBOL batch program blows past useful context or causes the model to lose track of working-storage layouts and control flow — and they skip building the structured metadata (copybooks, CICS maps, IMS PSB/DBD hierarchies, DB2 schema, call graphs) a COBOL system never documents about itself. Neither failure is something one developer reliably self-corrects under deadline pressure across a 10-million-line program with dozens of contributors — it's a governance and tooling gap.

Coding Agents Framework (CAF) closes that gap with a free, downloadable set of Python tools and a curated prompt library that encodes the discipline: automated COBOL-aware chunking, automated metadata extraction per legacy subsystem, and versioned prompt packs — handed off to whatever coding-agent platform the team already uses. CAF also ships an Eval Framework: tooling to mine golden datasets from the legacy system and a harness that runs them against LangSmith's evaluation tooling.

The framework itself is free. The entire revenue plan is one number: reach at least 100 tracked customers with LangSmith access attributable to this framework, then convert that proof into a flat $250,000/year referral fee from LangChain for driving enterprise adoption of LangSmith as the eval backend for coding-agent-driven modernization work.

This is a concentrated, single-counterparty revenue model with real chicken-and-egg risk: LangChain will not sign the deal on a pitch alone, and the 100-customer proof has to be built before the deal exists. See Path to $250K/Year and Risks & Mitigations.

2. The Problem

#ProblemWhy it hurts
1Context overload from naive chunking. COBOL batch programs are frequently single files of 5,000–20,000+ lines with deeply nested paragraph structures and GOTO-driven control flow.Pasting a whole program, or splitting it at arbitrary line boundaries, either exceeds useful context or severs paragraphs from the working-storage and condition-name definitions they depend on — the model starts hallucinating field types and business logic it can no longer see.
2Invisible, undocumented metadata. Copybooks are shared across dozens of programs; CICS maps, IMS PSB/DBD hierarchies, and DB2 DDL/referential structure exist outside the source files a developer would naturally paste into a prompt.Without this assembled as structured context up front, the coding agent is inferring record layouts and relationships it should be able to look up — the single largest source of subtly wrong conversions that pass a superficial code review.
3No shared process across developers or teams. Absent a common framework, each developer invents their own ad hoc chunking and prompting approach.Quality varies file to file and team to team on the same migration program — a governance problem, not a per-developer skill problem, and one that gets worse as the program scales to more contributors.
4No systematic way to measure conversion quality at scale. Spot-checking a sample of converted programs doesn't scale to 10 million lines.Building golden datasets and eval harnesses from scratch, per project, is expensive and in practice rarely done with any rigor — so quality problems surface in UAT or production instead of during conversion.

There is currently no widely adopted, free, purpose-built framework that enforces the chunking, metadata, and eval discipline a large legacy modernization program needs — independent of which coding-agent platform the team uses to actually generate the code. That gap is the business opportunity.

3. The Product & How It Works

What it is

A downloadable Coding Agents Framework (CAF): Python tools and a prompt library that discipline the inputs to whichever coding agent the team uses, plus an Eval Framework that measures the output. CAF does not convert code itself — it structures what goes in, and scores what comes out.

A. Discipline-as-Code (tools + prompts)
A COBOL-aware chunking engine, a metadata extraction pipeline (copybooks, CICS maps, IMS PSB/DBD, DB2 DDL, call graphs), a versioned prompt library per subsystem, and a local orchestration CLI that sequences extract → chunk → prompt → hand-off → capture.
B. Eval Framework
A golden-dataset generator that mines representative test cases from the legacy system, plus a harness that wraps LangSmith's evaluation tooling to score converted Java code for functional equivalence, business-rule adherence, and code quality.

MVP scope — COBOL → Java, modularized by legacy subsystem (chunking and metadata needs differ substantially by type):

PackWhy it needs its own tooling
COBOL BatchLarge, sequential programs; the chunking engine's primary use case — ships first as the highest-volume, most common entry point for a modernization program.
COBOL Online (CICS)Transaction/pseudo-conversational structure with BMS maps; metadata extraction must capture CICS command usage and map layouts, not just working storage.
IMSHierarchical database structure (PSB/DBD) — an entirely different metadata shape than the relational DB2 case.
DB2Relational schema and referential integrity extraction; DDL parsing and foreign-key/constraint mapping.
CICSTransaction definitions and region-level configuration, layered on top of the CICS Online pack for programs that need it.
User journey
  1. Team downloads and installs CAF locally — free, no signup wall for the core tooling.
  2. They point CAF at the COBOL/JCL/copybook source tree.
  3. CAF classifies programs by subsystem type and runs the matching metadata-extraction and chunking pipeline.
  4. CAF emits ready-to-use, context-scoped prompt packages per program or chunk.
  5. The developer feeds these into their coding agent of choice — Claude Code, Codex, or others — CAF disciplines the inputs, it doesn't do the conversion.
  6. The team uses the Eval Framework to generate or curate a golden dataset and runs the LangSmith-backed eval harness to score the converted code, then iterates on the feedback.

CAF is BYO-LLM and local-first — it works with any coding-agent platform, and the chunking/metadata tooling runs on the developer's own machine

4. Target Market

Primary customer persona: systems integrators running large COBOL mainframe modernization engagements on behalf of enterprise clients, and enterprise internal modernization/platform teams running the migration in-house.

Best starting industries (large legacy COBOL footprints, well-documented compliance pressure, clear ROI on getting the conversion right):

1. Banking & Financial Services
Core banking, payments processing, batch settlement — some of the largest and oldest COBOL estates in existence.
2. Insurance
Policy administration, claims processing — deep CICS/IMS/DB2 footprints, heavy batch processing.
3. Government & Public Sector
Benefits administration, tax systems — long-running mainframe estates under increasing modernization mandates.

Systems integrators are the highest-leverage channel, not just a segment. An SI adopting CAF as an internal accelerator gets a standardized, repeatable process across every client engagement — a much faster path to the 100-customer target (see Reaching 100 LangSmith-Referred Customers) than enterprise-by-enterprise adoption alone.

12. Strategic Advantage / Moat

  • Domain-specific tooling is hard to replicate quickly — encoding the chunking and metadata rules for COBOL Batch, CICS, IMS, and DB2 correctly requires real legacy-systems expertise, not just prompt engineering.
  • Zero price removes the adoption blocker — no budget approval, and because the core tooling runs locally, much less security-review friction than a paid or cloud-only alternative.
  • SI channel distribution advantage — landing a framework as an internal accelerator inside a systems integrator reaches every one of that SI's client engagements, not just one customer at a time.
  • The golden-dataset/eval infrastructure is the hard-to-replicate part — a coding agent doesn't spontaneously produce a rigorous, systematic eval harness; that infrastructure is what a modernization program manager actually needs before cutover, and what anchors the LangChain relationship.
  • Strong unit economics if the deal signs — near-zero marginal cost per additional customer once the tooling exists, against a flat $250,000/year fee that doesn't scale down with a smaller team.

15. Summary

Coding Agents Framework addresses a real, underserved gap in agentic-AI-driven legacy modernization: the inconsistency in COBOL-to-Java conversion quality is a process-discipline problem, not a model-capability problem, and no free, purpose-built tooling currently enforces the chunking, metadata, and eval rigor a multi-million-line migration needs — independent of which coding-agent platform a team uses. The product is free by design, because the business is not selling the framework; it's building a qualified, attributable enterprise pipeline into LangSmith, monetized through a single flat $250,000/year referral fee. That model is only as strong as the proof behind it: reaching ≥100 real, trackable customers with LangSmith access before or during negotiation with LangChain is the load-bearing milestone the entire plan depends on — and the single-counterparty concentration, the chicken-and-egg sequencing, and the local-first-vs-cloud-eval tension are the risks most likely to determine whether this plan works.
