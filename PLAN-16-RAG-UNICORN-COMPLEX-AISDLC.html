1. Executive Summary

The fundamental problem. A million lines of code is about 12 million tokens, or roughly 12 times the largest context windows available today. So the code has to be split, and how it is split decides the quality of the result. Split it by size or by text similarity, and the LLM sees a rule without the data definition, job setting or database table that changes what the rule means. The document reads well and is quietly wrong.

The product. CodeStrata treats this as a compiler problem, not a search problem. It first parses the whole system into a graph of calls, data and jobs. It then cuts the code by behavior into Context Packs and works bottom-up, so each LLM call gets the code it is explaining plus short, already-checked summaries of everything that code depends on. The LLM returns structured claims, not prose. Each claim is then tested and given a proof level before it reaches a document.

The evidence. The approach is sound and partly public. A 2026 study of a 3.4M-line COBOL system combined parsing with an LLM and reached 93% agreement with expert-written rules, cutting documentation effort by about 70%. Its informal LLM-only trials had more hallucinations, higher token cost and weaker coverage.1 That 93% also marks the opening: about 1 rule in 14 was still wrong, and human correction was typically needed.

The gap. Line-level traceability is no longer a differentiator, because AWS already offers it with a mainframe agent priced at $0.7 8 CodeStrata therefore has to win on three narrower things: proof of correctness rather than proof of origin, logic that crosses language boundaries, and a neutral knowledge layer that any coding agent can use across the software lifecycle.

Business model in one line: a fixed-price $75,000 Proof Assessment shows measured accuracy on a customer's own code, then converts to an annual subscription of about $100,000 per million lines that keeps the documentation current and feeds coding agents.
Honest verdict: the technical idea is strong, and token cost is not the obstacle: about $2,000 per million lines even with a 5× safety margin. The obstacle is commercial. This market has a free offer from AWS, Anthropic's own tools, CoreStory's $32M head start and in-house builds at banks. This plan estimates about a 1.5% chance of reaching $1B, below Plan 15's 2%. It needs a technical co-founder and about $173M of modeled funding, though its first six months can be done solo.

2. The Problem — A Million Lines Will Not Fit

Large legacy systems run core banking, insurance and government work. The people who understood them are leaving, and the documentation is thin or out of date. One widely cited survey, commissioned by a COBOL vendor, estimated 775–850 billion lines of COBOL in daily use, while other estimates run nearer 200 billion.15 The exact count matters less than the shape of the task: nobody can read these systems, so they want an LLM to do it.

Challenge 1: It does not fit

At an assumed 12 tokens per line, 1 million lines is about 12 million tokens. Current top models accept 1 million.16

A bigger window would not settle it. In one benchmark, moving from 10k to 30k tokens of context did not reliably help.2

Challenge 2: Meaning is far away

A rule's meaning can sit in a shared data definition, a database table, a batch job setting or a program five calls away. Text similarity finds none of those reliably.

Models tested on real repositories showed high precision but low recall on call chains: they got direct links right and missed deeper steps.2

Challenge 3: Nobody can check it

The output is thousands of pages, and the experts who could review it are the scarce resource that caused the problem.

Even with the right context supplied, the best model in that benchmark reached only 69.1% on predicting program output.2 Fluent documents can hide errors like these.

Why the common ways of feeding code to an LLM break at this scale
ApproachWhat it does wellWhat goes wrong at 1M+ lines
Fixed-size chunksSimple and cheapCuts through logic, and separates code from the data definitions that give it meaning.
One file at a timeRespects a natural boundaryA large legacy program can exceed a sensible budget, while shared logic lives in other files.
Vector retrieval (RAG)Finds similar text quicklySimilar is not connected. Top-k results cannot prove everything relevant was found, and retired copies look just like live code.
Whole system in long contextWorks for small systemsDoes not fit at this scale, and irrelevant files reduce accuracy.2
Agent explores on demandExcellent for one specific questionReads what it happens to find. It cannot show that the whole system was covered, and two runs can differ.
The core insight: "How do we chunk the code?" is the wrong first question. Code is not a pile of text. It has exact structure that a parser can recover with certainty. Use that structure to decide what the LLM reads, and save the LLM for what only it can do: explaining intent in plain language.

3. A Worked Example — One Late-Fee Rule

This scenario is illustrative and invented. An insurer has a 1.4M-line system built from COBOL, batch jobs, DB2 tables and a Java front end. The question is simple: when is a late fee charged?

The real answer has four parts in four places: program CLM2040 uses a 30-day default; a DB2 table raises it to 45 days for New York policies; a setting on the month-end batch job skips fees for hardship cases; and LATEFEE-OLD, which also says 30 days, was retired in 2009 but never deleted.

ApproachWhat the document saysResult
Fixed-size chunks"Late fees apply after 30 days."Reads well. Misses two conditions.
Vector retrievalBlends CLM2040 and LATEFEE-OLD, describing a rule from a program that no longer runs.Includes dead code.
Agent on demandFollows the call into DB2 and finds the New York rule.Better, but misses the job setting, which is not in any COBOL file.
CodeStrataStates all three live conditions, excludes LATEFEE-OLD as unreachable, and cites the evidence for each.Complete for what the graph can see, with a proof level on each claim.
The hardship setting is the important one. It never appears in the application code at all. No amount of better embedding finds it, because the link exists only in the system's job structure. Only a system-wide graph makes that connection visible.

4. The Vision — Compile, Then Explain

Plan 15 argued that company knowledge should be compiled, not re-read on every question. Code suits that idea even better, because it comes with a precise grammar, and it can often be run to test a claim about it.

Chunk and retrieveCompile and prove
Unit of workA slice of textA behavior: a transaction, job or API and what it reaches
Who picks the contextSimilarity scoreThe dependency graph, with a token budget
Order of readingAny orderBottom-up, so each caller inherits checked summaries
OutputProseStructured claims with evidence
"Did we cover it all?"UnknownA coverage map of every live line
When code changesStart againRecompute only what the change touches
Ideas this plan combines, and credits
  • Parse first, then generate. The ACL 2026 study showed deterministic analysis feeding an LLM on a 3.4M-line system.1
  • Bottom-up code summaries. Cisco researchers proposed summarizing a code graph bottom-up, so that higher-level summaries inherit context from their parts.3
  • Plan 14's Deterministic Layer. Use AI for judgment and scripts for everything repeatable.
  • Plan 15's Answer Receipts. Tie every statement to its evidence, and trace it again when the evidence changes.
What "proven" means here: CodeStrata does not claim to recover what the original programmers intended. It claims something narrower that a reviewer can check: what the code does, under which conditions, and what evidence supports that statement.

5. The Product & How It Works

Legacy estate: 1M+ lines

Source code, shared data definitions, job control, database schemas, config, logs and tests

1. Census (no AI)

Counts what exists. Separates live code from dead, duplicate and generated code, and expands shared definitions.

2. System Graph (no AI)

Parses every language into one graph of calls, data reads and writes, jobs and links between languages.

3. Slicer (no AI)

Cuts the graph by behavior and orders the work bottom-up. Builds a Context Pack for each unit of work.

4. Explainer (AI)

Reads one Context Pack and returns structured claims, each citing its evidence. Asks for more context when unsure.

5. Prover (mostly no AI)

Checks each claim against the graph, a second model and, where possible, real execution. Sends only the risky claims to an expert.

6. Publisher (when anything changes)

Builds documents and an agent-ready knowledge base. Recomputes only what a code change touches.

The answer to "how do we chunk it?": six slicing rules
RuleWhat it meansWhat it prevents
1. Remove before you readExclude unreachable, duplicate and generated code.Paying to document code that never runs.
2. Expand before you cutResolve shared data definitions and macros first.Logic that seems to use undefined fields.
3. Slice by behaviorStart at entry points such as transactions, jobs and APIs, and follow what they reach.Boundaries that make sense only to a file system.
4. Work bottom-upExplain called code first, treating loops of mutual calls as one unit.Reading the same deep code over and over.
5. Replace code with contractsCallers receive a short checked summary of called code, not its source.Running out of context. This is what lets 12M tokens fit through a small window.
6. Budget and accountHold each pack to a fixed token budget, and record that every live line was covered.Silent gaps in the documentation.
What goes in a Context Pack
Target code

The exact routine or region being explained.

Callee contracts

Checked summaries of what it calls.

Touched data only

The fields, tables and files it reads or writes, not whole schemas.

Caller context

How it gets invoked and with what settings.

Runtime evidence

Job settings, logs or test results when available.

Glossary

Field names already decoded into business terms.

The pack budget, about 60,000 tokens in this plan, is an assumption to tune. Stage 0 must test whether smaller packs read better.

Proof levels: the Prover's scale
LevelWhat was shown
1Cited lines exist and contain the named items.
2The System Graph agrees with the claimed flow.
3A second model, seeing only the evidence, could not refute it.
4A test or real execution matched the claim.
5A named expert signed it off.

Traceability alone cannot ensure correctness, as the ACL study itself notes.1 Levels 3–5 are the difference between "this came from line 42" and "this is true."

The four hard engineering problems
  • Hidden links. Dynamic calls, program names held in data and vendor frameworks can leave gaps in the graph. Every unresolved link must be shown, not ignored.
  • Summary drift. A small error in a low-level contract spreads upward through every caller. Contracts need the strictest checks.
  • Dialect long tail. Each customer has its own compiler options, macros and in-house tools, and the parser has to handle them.
  • Execution access. Level 4 proof needs a way to run the code. Many legacy systems lack test environments or safe data.
From documents to an AI SDLC

Reverse engineering is a one-time project. The recurring value comes from reusing the same knowledge at every lifecycle stage.

  • Understand: system, domain and rule documents.
  • Plan: impact analysis before a change is approved.
  • Build: Context Packs served to any coding agent over MCP.
  • Test: test cases generated from claims.
  • Modernize: specifications that feed a conversion pipeline such as Plan 6's LegacyClaw.
  • Maintain: documents updated with each code change.

7. Target Market

Beachhead: mixed-language estates at North American banks and insurers

The first job: "Show me what this system really does, how sure you are, and what would break if we changed it." The economic buyer is the CIO or Head of Modernization, supported by the architects who will rely on the result.

Why not simply COBOL? A pure mainframe-to-AWS project already has a free option. The opening is an estate where logic crosses COBOL, batch jobs, stored procedures, Java and .NET, and where the customer may not be moving to AWS at all. Plan 8's list of 109 named BFSI accounts is a starting point. The catch is 9–18 month sales cycles and strict rules on code leaving the building.

What it is worth

Morgan Stanley's reported figures imply about 31–59 hours saved per 1,000 lines. At an assumed $100 an hour, that is about $3–$6 per line, or $3M–$6M per million lines.4 5

Self-reported by one bank, across work broader than documentation. It is a rough ceiling, not a price benchmark.

Why pay when AWS is free?

A buyer pays only if at least one of these is true: the free output is not accurate enough to trust, the logic crosses code the free tool does not handle, or the customer is not moving to AWS.

Kill Test 3 requires a side-by-side result against the free option. AWS moved code transformation to no cost in March 2026,9 though it notes that future capabilities may become paid.7

How the average contract reaches $650k: customers start with about 2M lines and add systems, reaching about 6.5M. The model needs net revenue retention near 140% in the early years, which must be proven, not assumed.

A warning on recurring revenue: reverse engineering can be a one-time purchase, and a system that gets migrated may leave the subscription. If customers do not use Living Docs and Agent Context month after month, this is a project business, and the ARR model below fails.

14. Strategic Advantage / Moat

A startup has no moat on day one. These advantages build up only if the company survives long enough, roughly in the order listed.

The expert-verified record

Each expert decision adds to a checked account of how a system behaves. Once the people who knew it have retired, that record cannot be recreated. This is the strongest lock-in.

A library of dialects

Every deployment adds parsers and edge cases for real-world legacy code. This is slow, unglamorous work that a general model does not replace, and it compounds.

Neutrality

Customers run several clouds, models and agents. A cloud vendor has a reason to steer the migration; an independent layer does not.

The benchmark

Owning a credible test shapes how buyers judge the category. Accuracy data across many estates could also show which code is hardest to document, and why.

17. Summary

The hardest part of reverse engineering a large system is not writing the document. It is deciding what the LLM should read, then knowing whether what it wrote is true. Chunking by size or similarity fails because code's meaning follows its structure, not its text.

CodeStrata's answer is to compile first: find what is live, build a graph of the whole system, slice it by behavior, work bottom-up with checked summaries, and treat every statement as a claim to be proven. Token cost is small. Expert time, trust and recurring use are what decide the outcome.

Next step: run AWS Transform and Claude Code on CardDemo, hold 20 interviews, build MaskedDocs-Bench, and let the five kill tests decide. If they pass, this becomes a venture-scale company with a roughly $1B target. If they fail at the last two stages, the assessment work may still support a solo business. Either way, the next six months are affordable.
