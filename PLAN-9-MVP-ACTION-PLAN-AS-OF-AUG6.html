1. What Has Been Achieved

All of this lives in the working repo today, not on a roadmap: COBOL-TO-JAVA-CONV-PROJ2\ (the generalized converter), JAVA-CODE-CREATED-BY-CONVERTER\PROJ1-BATCH-APP\ and JAVA-CODE-CREATED-BY-CONV-PROJ2\PROJ2-BATCH-APP\ (two real generated Java APIs, both currently running and testable), and INFO\HOW-JAVA-APIS-WORK-PROJ1-PROJ2.html (the detailed technical account this status update is grounded in). This is also, formally now, the proof point that justified the pivot: PLAN-9-CODING-AGENTS-FRAMEWORK.html has been updated to make the deterministic engine demonstrated here the plan's lead product, not a side experiment (see §3).

A full COBOL Batch parsing & codegen pipeline

Lexer, statement-boundary extraction, copybook/working-storage/PIC-clause/OCCURS/INDEXED BY parsing, call-graph discovery, and idiomatic Java codegen — automatically classifying each COBOL program's structural role (lookup, dispatch, orchestration, formatter, sort) and generating immutable Java records vs. mutable POJOs based on real write-once analysis, BigDecimal at every money field, Optional<T> at lookup boundaries.

A generalized batch-job orchestration layer

build_batch_app.py generates a complete Spring Boot REST + CLI app from a one-file project.yaml pointed at a target codebase — proven not hardcoded to one shape, across two independently-built real codebases (2 external inputs vs. 3; one subprogram owning 2 input files, three owning 0; different call-graph depths).

A working, local, zero-cloud-dependency eval harness

Runs the real COBOL through real GnuCOBOL as the oracle, runs the generated Java against the same input, and byte-diffs both. Not a design — a passing test suite, today: 1,797/1,797 lines identical (PROJ-1), 333/333 lines identical (PROJ-2).

Config-driven "point it at a new codebase" onboarding

Adding PROJ-2 required zero generator code changes beyond the generalization pass itself — one new project.yaml (source directory, entry program, a fixture path per real input file). This is the plan's own "team points CAF at their source tree" user-journey step, working today for the Batch pack.

Two real, demoable end products

Full Spring Boot REST APIs + CLI runners for both PROJ-1 and PROJ-2, each with an interactive Flask-based tester (input-data generator, browser UI) — something an SI or enterprise pilot contact could actually be shown running, not a slide.

Real documentation, not placeholder docs

HOW-TO-RUN-JAVA-API*.md, HOW-JAVA-APIS-WORK-PROJ1-PROJ2.html, HOW-TO-TEST-JAVA-API-AND-HOW-TESTER-WORKS.html — step-by-step, verified-by-actually-running-it documentation for both generated apps, plus a full narrative account of how each build session found and fixed real bugs.

3. The Scope Question — Resolved via Pivot

Resolved, August 2026: this section originally flagged an unresolved tension between what the plan described and what actually got built for the Batch pack. It has since been decided — PLAN-9-CODING-AGENTS-FRAMEWORK.html now formally adopts the deterministic-first approach as the plan of record, with the rationale stated plainly in its own updated Executive Summary: a shop won't extend trust on a discipline-layer pitch alone, but will extend it fast after seeing byte-for-byte proof on its own code. The comparison below is kept as a record of what changed and why, not as an open question anymore.

The original plan described CAF as a discipline layer: chunk the COBOL, extract metadata, produce context-scoped prompt packages, then hand off to whatever coding agent the team already uses (Claude Code, Codex, etc.) to actually generate the Java, with the Eval Framework scoring whatever that agent produced. What actually got built for the Batch pack was different in kind, not just further along: a fully deterministic, non-LLM transpiler that reads the COBOL AST directly and generates the Java itself. That difference is now the plan's own lead product, with the original discipline-as-code path retained explicitly as the fallback for whatever resists full determinism (CICS/IMS Online most of all — see §4).

Plan's original approachWhat was actually built (Batch pack)
Who converts the codeWhatever coding agent the team already uses (BYO-LLM)A deterministic Python transpiler — no LLM at conversion time
Context-window riskReal — needs careful chunking of 5,000–20,000-line programsDoesn't apply — the transpiler parses the full COBOL AST directly
Correctness proofEval Framework scores the agent's output after the factByte-for-byte equivalence against real GnuCOBOL, proven at generation time
Platform independenceWorks with any coding agent, a real differentiator in the planDoesn't need one — but also isn't "BYO-LLM" anymore for this pack
Where this likely still breaks down—CICS/IMS/DB2 are less structurally uniform than Batch; a full deterministic transpiler may not generalize the same way there — this is exactly why the discipline-as-code fallback path was kept, not dropped, in the revised plan

What was decided: the Batch pack's deterministic-transpiler approach is the new plan of record, not a wrapped eval-oracle inside the original chunk-and-hand-off shape. The "prompt library" line item was redefined (not dropped) into a smaller, explicitly-secondary "discipline-as-code fallback path" (§2), and the pitch to LangChain/SIs changes from "we discipline your coding agent" to "we auto-convert what we can deterministically, and discipline the rest" (see the updated plan's own Executive Summary and Moat sections). The open risk that remains is technical, not strategic: whether determinism actually generalizes to CICS/IMS Online as well as it did to Batch — tracked as a named risk in the updated plan, not resolved by this decision alone.

7. Summary

As of August 6, the highest-technical-risk piece of the original MVP — COBOL parsing, metadata extraction, and automated conversion for the Batch subsystem — is not just de-risked but working and proven, twice over, against real GnuCOBOL output with zero cloud dependency. That result was strong enough to change the plan itself: the strategic question this report originally raised (§3) is now resolved, with the deterministic-first approach adopted as the plan of record and the roadmap deliberately expanded to VSAM, DB2, IMS, and CICS/IMS Online.

That expansion is real, not cosmetic — the revised build-hour estimate is roughly double the original (~715–1,085 hrs vs. ~410–605), which is why the "percent delivered" figure in this report dropped from ~45–55% to ~20–25% even though nothing already built shrank. Sequencing matters more now than it did before the pivot: VSAM and DB2 fit inside Year 1 alongside distribution; IMS and CICS/IMS Online realistically belong in Year 2.

Two things remain almost entirely untouched: the LangSmith attribution/receipts layer the referral-fee mechanism depends on — now deliberately split from a larger eval-scoring harness that's correctly deferred to Year 2, so this piece is small and unblocked, just not yet started — and every single customer-facing distribution channel (0% of the 580–975 planned distribution hours have started). The technical build has outpaced the go-to-market motion, and the pivot gives distribution a stronger opening move than it had before — the next phase of work should put that to use, not add more technical scope beyond the Year-1 sequence already laid out in §4 and §6.
